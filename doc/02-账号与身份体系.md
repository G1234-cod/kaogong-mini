# 02 · 账号与身份体系

> 账号 = 微信 openid。没有白名单、没有注册表单、没有密码、没有手机号。用户感知层面只有两个选择：**试玩** 或 **正式开始**。

## 决策记录（为什么这样设计）

| 决策 | 结论 | 理由 |
|------|------|------|
| 白名单 vs 注册制 | **注册制**（任何人可自选成为正式用户） | 主理人不需要每次 SSH 上服务器加白名单；亲友扫码即可自注册；陌生访客有游客通道兜底，不怕滥用（游客数据不落库） |
| 账号标识 | openid（微信自动下发） | 个人主体小程序拿不到手机号（`getPhoneNumber` 需企业认证）；`getUserProfile` 昵称接口已收紧；openid 静默无感，体验最好 |
| 游客数据 | **本地沙盒，不落服务器**；转正时弹窗询问是否带走 | 服务器不被陌生访客灌数据；试玩期成果不丢失 |
| 游客身份 | 落一条 users 表记录（role=guest）+ last_seen | B 端统计"今天来了多少人"连游客都算得进；主理人能看到"谁来过"，避免旧版翻 journalctl 日志的窘境 |
| 登录次数 | 首次选择后**永久免登** | token 180 天有效；过期静默重登，用户全程无感，不出现登录界面 |
| 数据规模 | 全量上云，SQLite 承载 | 统计是 B 端硬需求 → 数据必须在服务端；实测估算 1 用户 ≈ 1MB/年，1000 用户 ≈ 1GB，SQLite 毫无压力，备份 = 拷文件 |

## 首次打开：二选一选择屏

新用户（无缓存 token、无 `kg-role-chosen` 标记）首次启动时，bootstrap 流程前插入**身份选择屏**（全屏两个大按钮）：

```
┌─────────────────────────────┐
│   欢迎使用考公小助手 🎉      │
│                             │
│  ┌───────────────────────┐  │
│  │ 🎮 试玩看看            │  │  → role=guest：注入演示数据（fixtures 五件套），
│  │   用准备好的数据逛一圈  │  │    数据只存本地；设置页可随时升级
│  └───────────────────────┘  │
│  ┌───────────────────────┐  │
│  │ 🚀 正式开始            │  │  → role=user：微信静默注册建档，
│  │   我的记录自动云端同步   │  │    数据全量上云，换机/清缓存不丢
│  └───────────────────────┘  │
│  底部小字：《隐私政策》链接   │
└─────────────────────────────┘
```

- 选择结果写 storage `kg-role-chosen`，之后每次打开**跳过选择屏**直接静默登录
- 两个按钮都先走 `Taro.login()` 拿 code，区别只在请求参数（见下）

## 登录链路

```
小程序启动 app.ts onLaunch
  → bootstrap()
    → 读缓存 token（storage kg-auth）有效？
        ├─ 有效 → 直接 getSnapshot() hydrate → ready
        └─ 无效/过期 → Taro.login() 拿 code
             → POST /auth/login {code, register: boolean}
                  ← {role, openid, token}
             → role=user   → getSnapshot() → hydrate → ready
             → role=guest  → hydrate(fixtures 演示数据) → ready
```

接口语义（对现有 `POST /auth/login` 的扩展，改造点见 06 文档）：

- `register: true`（"正式开始"）→ 服务端 code2Session 得 openid，users 表无记录则建档 `role=user`，有记录沿用原角色（老用户重装/换机后走这条直接续档）
- `register: false`（"试玩"）→ openid 落 users 表一条 `role=guest` 记录（无记录时创建，更新 `last_seen_at`），**不建数据档**
- dev 模式（未配 AppSecret）：code 派生稳定伪 openid，便于开发者工具联调（现有逻辑保留）

token 机制（`server/security.py`）：HMAC 签名无状态 token，有效期 180 天，payload 即 openid。过期 → 前端捕获 401 → 静默重走登录链路，用户无感。

## 游客模式

| 项 | 行为 |
|----|------|
| 数据注入 | `buildGuestData()`（`src/mocks/fixtures.ts`）生成演示五件套：30 天省考倒计时 / 15 天全勤热力图 / 3 张待复习闪卡 / 三件事 2/3 / 智能午餐推荐，另有心情、账本、番茄钟、奖券等氛围数据，日期全部相对 `todayStr()` 动态生成 |
| 写入隔离 | `storageTransport` 按 role 选命名空间：guest 全部写 `kg-guest-data`，user 写 `kg-data`（见 [03](./03-数据模型与同步.md)） |
| 服务端写拦截 | httpTransport 阶段：guest 调 `/data/keys` 服务端返回 `{ok:true, discarded:true}` 接受但不落库（现有逻辑） |
| 升级入口 | 设置页身份卡常驻「升级为正式账号」按钮 |
| 清空试玩 | 设置 account 子页提供「清空试玩记录」：仅清 `kg-guest-data` 命名空间 |

## 转正（游客 → 正式用户）

设置页点「升级为正式账号」后：

1. `appConfirm` 弹窗：「要把试玩期间的记录带到新账号吗？」→ **带走** / **重新开始**（discard 试玩数据）
2. `POST /auth/upgrade`（Bearer 当前的 guest token）→ 服务端把 users 记录改 `role=user` → 返回新 token
3. 前端把本地 role 置 user 并 rebootstrap：
   - 选"带走"：读 `kg-guest-data` 全量 → `writeOps` 逐域上传（走真实 transport 落库）→ 切换命名空间 → hydrate
   - 选"重新开始"：直接切命名空间 hydrate（DEFAULTS）
4. **关键坑**（历史上最易踩）：若跳过第 3 步直接 hydrate，服务端 snapshot 为空 → DEFAULTS 覆盖 → 沙盒数据"全部消失"。转正上传必须发生在首次 user hydrate 之前

## 昵称与账号展示

- 用户自填昵称：settings 页 `appPrompt` 输入，存 `user_data` 的 `settings` 域内字段（`settings.nickname`），用户端奖券/弹窗文案可用
- B 端备注：users 表 `nickname` 字段由 B 端编辑（主理人视角"这是谁"，如"媳妇/表弟/面试演示号"），与用户自填昵称是两个字段，互不覆盖
- account 子页展示：当前身份徽章（正式用户/试玩中）、openid 尾号、昵称、数据同步说明（"数据实时云端同步，换机不丢"）

## 隐私与合规（提审卡点）

1. **《隐私保护指引》**：小程序后台填写，声明收集"微信openid（账号识别）、学习打卡数据、偏好设置"，用途"仅用于账号识别与数据同步，不对外提供"
2. `requiredPrivateInfos: ['getLocation']` 已在 `app.config.ts` 声明（天气定位用）；若不想申请定位权限，可在提审版暂时移除该行 + 隐藏定位按钮，仅留城市手动搜索
3. UI 文案敏感词清零（`AI|大模型|GPT`）：`constants/copy.ts` 集中管控 + grep 验收（见 [01](./01-项目总览.md) 原则底线 6）
4. 类目：工具类；无支付、无社交、个人主体可用

## 旧 PWA 存量迁移

5 位旧用户的真实数据还在旧 PWA 的 IndexedDB（设备本地）。旧 PWA 拿不到微信 openid，无法自动迁移，采用**B 端手动导入**（一次性操作）：

1. 旧 PWA 设置 → 数据备份 → 导出 JSON（version 2 格式，含全部顶层键）
2. 让该用户先用微信打开小程序选择"正式开始"（产生 openid + users 记录）
3. B 端 → 备份页 → 粘贴 JSON + 从用户列表选目标用户 → `POST /admin/import`（服务端校验并逐域写入 `user_data`）
4. 用户下次打开小程序，snapshot 拉到导入数据，完成迁移

接口与校验细节见 [06](./06-后端API契约.md)、操作界面见 [07](./07-B端管理后台.md)。
